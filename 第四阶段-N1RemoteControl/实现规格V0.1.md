## 2. 清单与权限

Manifest 只申请运行所需权限：

```xml
android.permission.BLUETOOTH
android.permission.BLUETOOTH_ADMIN
android.permission.ACCESS_FINE_LOCATION
android.permission.INTERNET
android.permission.WAKE_LOCK
android.permission.ACCESS_WIFI_STATE
android.permission.CHANGE_WIFI_STATE
android.permission.RECEIVE_BOOT_COMPLETED
```

说明：

- Android 7.1 读取已配对设备需要定位权限。
- `INTERNET` 只允许回环、家庭局域网或 Tailscale 监听；应用不访问 HT 云端。
- `WAKE_LOCK`、Wi-Fi 锁和屏幕常亮用于维持 N1 常驻，不代表允许发射。
- 不申请麦克风、存储、相机、电话、悬浮窗或系统设置修改权限。
- `MainActivity` 导出；`GatewayService` 和内部组件不导出；`BootReceiver` 只处理系统受保护广播。

## 3. 线程与组件规则

```text
MainActivity
  | 固定左侧菜单、五个单屏页面、本地配置、令牌、日志、启停
  v
GatewayService（前台服务）
  |-- RadioSession（唯一实例、链路 epoch）
  |     |-- BluetoothLink（RFCOMM 收发）
  |     `-- CommandScheduler（串行请求）
  |-- StatusRepository（不可变快照）
  |-- LowRiskWriteController（单操作状态机）
  |-- LocalWebServer（有界 HTTP 线程）
  |-- AuthManager（令牌、会话、限流）
  |-- SseHub（SSE 客户端与心跳）
  `-- AuditStore（脱敏审计）
```

硬性规则：

1. 只有 `BluetoothLink` 可以读写 `BluetoothSocket`。
2. 所有 GAIA 请求只能进入 `CommandScheduler`。
3. HTTP 线程不能直接构造或发送 GAIA 帧。
4. 写请求必须通过 `LowRiskWriteController`，并且仅在 `GaiaCodec.isAllowedWriteCommand()` 白名单内通过。
5. 同一时间最多一个控制操作；读取轮询和状态通知不得与在途操作产生响应错配。
6. `StatusRepository` 使用不可变快照，网络线程不得在锁内执行蓝牙 I/O。
7. SSE 只发送摘要事件，完整状态由客户端重新拉取 `/api/v1/snapshot`。

## 4. GAIA 与解析实现

基础帧：

```text
FF 01 FLAGS LENGTH 00 02 CMD_HI CMD_LO [PAYLOAD...]
```

读取白名单：

```text
GET_DEV_INFO(4)
REGISTER_NOTIFICATION(6)
READ_SETTINGS(10)
READ_RF_CH(13)
GET_HT_STATUS(20)
GET_VOLUME(22)
```

写入白名单：

```text
WRITE_SETTINGS(11)
SET_VOLUME(23)
```

### 4.1 音量

- 请求载荷为单字节 `volume`。
- 允许范围 `0..15`。
- 写入后延迟 900 毫秒读取 `GET_VOLUME`。
- 回读值必须等于目标值；读取失败或值不同进入回读失败路径。

### 4.2 扫描与 A/B

- `READ_SETTINGS` 返回完整设置载荷。
- `SettingsBlock` 保存完整的原始字节副本，不允许 HTML/JSON 直接编辑任意字段。
- 扫描只切换完整载荷中的扫描位。
- A/B 只切换完整载荷中的当前侧位。
- 回读必须将整个设置载荷与预期载荷逐字节比较，而不是只比较一个字段。
- 任何载荷不足 10 字节、命令不匹配或响应状态不为 0时，拒绝参与写入。

## 5. 控制状态机

### 5.1 正常流程

```text
submit
  -> ACCEPTED
  -> BASELINE_READ
  -> WRITING
  -> READBACK
  -> READBACK_OK
```

- `submit` 成功返回 HTTP 202 和 `CONTROL_ACCEPTED`。
- 基线读取发生在操作线程，不在 HTTP 线程阻塞等待。
- 写入只发送一次，不做自动重试。
- 回读成功后操作进入终态，允许下一项控制。

### 5.2 异常流程

```text
基线尚未有效 -> TIMEOUT / UNAVAILABLE，不自动回滚
已写但回读不匹配 -> READBACK_MISMATCH -> ROLLBACK_WRITING -> ROLLBACK_OK/ROLLBACK_FAILED
12 秒操作超时且已写 -> ROLLBACK_WRITING
链路 epoch 改变 -> LINK_LOST / CANCELLED
已有操作未结束 -> CONTROL_BUSY
```

保护参数：

| 参数 | 值 |
| --- | ---: |
| 操作总超时 | 12000 ms |
| 回滚超时 | 8000 ms |
| 回读延迟 | 900 ms |
| 回滚次数 | 最多 1 次 |
| 控制并发 | 1 |

回滚使用的是基线完整设置块或基线音量，不是页面当前显示值。回滚失败必须保留 `ROLLBACK_FAILED`，不能静默宣称成功。

## 6. HTTP 接口实现

### 6.1 通用鉴权

- 支持 `Authorization: Bearer <token>`。
- 登录成功设置 `HttpOnly; SameSite=Strict; Path=/; Max-Age=43200` Cookie。
- 令牌长度为 10 位；服务端保存 SHA-256 而不是明文。
- 控制器和快照接口必须经过鉴权；健康检查和登录页不需要鉴权。
- 令牌不得放在 URL 查询串中。

### 6.2 `GET /api/v1/control`

返回控制状态：

```json
{
  "ok": true,
  "available": true,
  "busy": false,
  "state": "READBACK_OK",
  "kind": "VOLUME",
  "operationId": "ctl-1",
  "target": "4",
  "baselineDisplay": "音量 3",
  "expectedDisplay": "音量 4",
  "observedDisplay": "音量 4",
  "reason": "READBACK_MATCH",
  "updatedAt": "2026-11-28T03:00:00Z",
  "epoch": 7,
  "sent": true,
  "rollbackSent": false
}
```

未完成或未执行操作时，相关字段可以为 `null`。状态值至少包括：

```text
IDLE, ACCEPTED, BASELINE_READ, WRITING, READBACK,
READBACK_OK, READBACK_MISMATCH, ROLLBACK_WRITING,
ROLLBACK_OK, ROLLBACK_FAILED, TIMEOUT, BUSY, UNAVAILABLE,
LINK_LOST, CANCELLED
```

### 6.3 提交控制

所有提交接口要求 `Content-Type: application/json`，请求体最多 1024 字节，且必须含 `confirm:true`：

| 路径 | 请求体 | 参数规则 |
| --- | --- | --- |
| `POST /api/v1/control/volume` | `{"volume":4,"confirm":true}` | volume 为 0..15 整数 |
| `POST /api/v1/control/scan` | `{"scan":true,"confirm":true}` | scan 为布尔值 |
| `POST /api/v1/control/side` | `{"side":"B","confirm":true}` | side 只能是 `A` 或 `B` |

成功返回 HTTP 202：

```json
{
  "ok": true,
  "accepted": true,
  "code": "CONTROL_ACCEPTED",
  "operationId": "ctl-1",
  "state": "ACCEPTED",
  "action": "volume"
}
```

调用方随后轮询 `GET /api/v1/control`，直到状态进入 `READBACK_OK` 或终态错误。HTTP 202 只代表操作受理，不代表电台已经写入成功。

### 6.4 错误响应

统一错误体：

```json
{
  "ok": false,
  "code": "CONFIRMATION_REQUIRED",
  "message": "控制操作必须显式包含 confirm:true",
  "requestId": "local"
}
```

| HTTP | 代码 | 场景 |
| ---: | --- | --- |
| 400 | `CONFIRMATION_REQUIRED` | 缺少显式确认 |
| 400 | `VOLUME_OUT_OF_RANGE` | 音量不是 0..15 整数 |
| 400 | `SCAN_OUT_OF_RANGE` | 扫描不是布尔 |
| 400 | `SIDE_OUT_OF_RANGE` | A/B 不是 `A` 或 `B` |
| 400 | `BAD_JSON` | JSON 格式错误或缺少字段 |
| 401 | `AUTH_REQUIRED` | 无鉴权 |
| 401 | `AUTH_FAILED` | 令牌或会话无效 |
| 409 | `CONTROL_BUSY` | 已有控制操作未完成 |
| 413 | `PAYLOAD_TOO_LARGE` | 请求体超过 1024 字节 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 不是 JSON |
| 429 | `RATE_LIMITED` | 登录或客户端限制触发 |
| 503 | `RADIO_NOT_READY` | 蓝牙或控制会话未就绪 |
| 503 | `CONTROL_TIMER_UNAVAILABLE` | 定时器不可用 |
| 503 | `CONTROL_CALLBACK_UNAVAILABLE` | 回调执行器不可用 |

## 7. 页面实现

### 7.1 安卓原生页面结构

- 微信绿色顶部标题栏，固定左侧菜单，右侧 `FrameLayout` 页面容器。
- 左侧菜单固定为运行状态、蓝牙电台、网络设置、运行选项、网关与令牌。
- 五个页面在启动时构建，通过 `VISIBLE/GONE` 切换；一次只显示一个页面。
- 选中菜单项使用绿色背景和白色文字，未选中项透明并使用深灰文字。
- 菜单支持点击和焦点导航，运行状态页占满右侧剩余高度。
- 不使用 `ScrollView`、`PositionStableScrollView`、上翻/下翻/到底、鼠标滚轮处理或滚动锚点。
- 目标分辨率 1920×1080，每页必须在一屏内完整显示。

### 7.2 远程网页结构

- 微信风格配色，移动端和桌面端自适应。
- 顶部显示网关、连接、电台、当前信道、扫描和 revision。
- 页签：总览、远程控制、设备、信道、网关、诊断、关于。
- 远程控制页显示音量、扫描、A/B 三项卡片，不使用频率、PTT 或音频控件。

### 7.3 控制交互

1. 用户选择目标值后先显示当前基线和目标值。
2. 点击确认后发送带 `confirm:true` 的 JSON。
3. 页面显示 `202 ACCEPTED`，轮询控制状态，不把受理当作成功。
4. 状态为 `READBACK_OK` 时显示“回读确认成功”，并清理目标脏值。
5. `READBACK_MISMATCH`、`ROLLBACK_*` 和超时状态显示明确错误，不隐藏回滚结果。
6. 控制页在操作未结束时禁用所有控制按钮。

## 9. 实机测试规格

只读检查：

```powershell
pwsh -NoProfile -File .\tools\Test-LiveGateway.ps1 `
  -TokenFile <本地令牌文件> `
  -BaseUrl http://<N1地址>:8710
```

低风险写入与恢复：

```powershell
pwsh -NoProfile -File .\tools\Test-LiveControl.ps1 `
  -TokenFile <本地令牌文件> `
  -BaseUrl http://<N1地址>:8710 `
  -ExecuteWrites
```

脚本必须先保存音量、扫描和 A/B 基线；每一步执行后检查控制状态和回读结果；无论成功或失败都尝试恢复原值。令牌文件必须是本地受保护文件，不能提交、打印到日志或放进 URL。

## 10. 验收判定

软件验收通过的最低条件：

- 111 项离线门禁全部通过。
- APK 签名、v2/v3 校验和 zipalign 通过。
- 真实 N1 登录、页面、快照、SSE 全部通过。
- 三项写入均达到 `READBACK_OK`。
- 最终音量、扫描、A/B 与测试前一致。
- 最终状态不是发射状态。
- 未经执行的 PTT、音频、频率、亚音、带宽或信道记录写入不得写成通过。

当前 0.4.1 已满足构建、签名、清单、原生单屏界面和版本门禁；控制服务与 0.4.0 相同，因此沿用 0.4.0 已完成的三项写入实机闭环，本版没有重新执行写入。两小时长稳、N7500 实际断电、实际 iPhone/Tailscale 和重复 50 次稳定性仍属于后续门槛，不能由本次短测替代。

## 11. 发布检查

1. 运行离线测试，确认 111 项。
2. 确认版本 `0.4.1`、versionCode `16` 与 Manifest、API 合同、网页页脚和原生页脚一致。
3. 校验 APK SHA-256、v2/v3 签名和 zipalign。
4. 安装到真实 N1 后检查健康页、前台服务、屏幕常亮、HT 官方应用未运行，并逐页切换五个左侧菜单。
5. 确认 1920×1080 下每页完整显示、无上下滚动，且旧上翻/下翻/到底入口不存在。
6. 执行登录/快照/SSE 自动检查，不输出令牌。
7. 仅当控制服务或白名单发生变化时执行三项写入和恢复，确认最终状态；纯界面版本不得重复危险写入。
8. 扫描仓库，确认无令牌、IP、MAC、日志或 keystore。
9. 更新阶段 README、总 README、设计、规格、API 和验收记录后提交推送。

## 12. 结论

0.4.1 的工程重点是在不改变控制白名单和状态机的前提下，把安卓原生界面压缩成固定左侧菜单的单屏结构，并彻底删除上下滚动和旧翻页实现。PTT、音频和高风险写入仍没有代码路径；任何后续扩展都必须先补齐稳定性和发射安全验收，不能绕过本规格的白名单与状态机。
